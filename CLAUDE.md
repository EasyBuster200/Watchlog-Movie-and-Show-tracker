# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Watchlog** (formerly TVTimeClone) is a TV Time–style movie/show tracker: browse trending content, save it to lists, track what you've watched (per-episode for shows), and mark favorites. Runs as a fully local, offline-first Android app (via Capacitor), and the same files are published as an installable web app (PWA) for iPhone, with per-device "profiles" instead of server accounts — there is no backend (the web host only serves the app's files). All movie/show metadata comes live from TMDB, called directly from the device using each profile's own TMDB API key.

This is a standalone repo, split off from [Movie-and-Show-tracker-Website](https://github.com/EasyBuster200/Movie-and-Show-tracker-Website) (a separate repo, not a branch of this one) at the commit that rebuilt the original server-backed multi-user website into this local-first app. Full history from before the split — including the original Express/SQLite server-backed version — is preserved in this repo's own git log; that other repo is the actively maintained website version if you need to compare current behavior against it.

**What's planned next** (optional online accounts that sign in with an account key plus a recovery email, local-first sync, friends, an admin page, all on Cloudflare) is in `docs/ROADMAP.md`, along with the decisions already made. Phase 1, the web app (PWA), is done and live at https://watchlogtracker.com (see "The web app" below). Phases 2 to 4 are built: the server (see "The server" below), online accounts with the TMDB proxy and the recovery email (Phase 3) and sync (Phase 4, "Sync in the app" below), the admin page with approval-based sign-up, Web Push to the owner, new keys by email, burst limits and Turnstile (Phase 8 parts 1 and 2, "Admin and sign-ups" below), notifications through the server for the web app (Phase 6, "Server notifications" below), and friends steps 1 and 2 (Phase 7, "Friends" below). Online accounts are shown to everyone. The rest isn't built yet. Check it before designing anything in that area. Repository workflow (branches and PRs, never rewrite `main` because `versionCode` is the commit count, CI) is in `docs/DEVELOPMENT.md`'s "Working on the repository".

## Commands

```bash
npm install       # install dependencies
npm run sync       # npx cap sync android — copies public/ into the Android project
npm run open:android  # npx cap open android — opens the project in Android Studio
npm test          # node --test tests/ — runs the localApi.js/standardItem.js unit tests
npm run test:server  # node --test server/test/*.test.js — the Worker's server tests (Node 22.5+, node:sqlite)
```

There is no build step, bundler, or lint config for the web layer — `public/` is plain HTML/CSS/JS loaded directly via `<script>` tags, and Capacitor just wraps it in a WebView (`android/app/src/main/assets/public/` is a synced copy, gitignored, regenerated by `npm run sync`). `npm test` runs the Node test suite in `tests/` (see Testing below).

No `.env`/server-side secrets are needed — each profile supplies its own TMDB API key through the UI (profile-picker.html), stored in `localStorage`.

**Building and installing on a phone:** `npm run sync`, then `cd android` and run `./gradlew assembleRelease` with `JAVA_HOME` pointing at a JDK 17 (on this machine `C:/Program Files/Java/jdk-17`) and `ANDROID_HOME` at the SDK. The APK is `app/build/outputs/apk/release/app-release.apk`; install with `adb install -r`. `versionCode` is the commit count (`git rev-list --count HEAD`) and `versionName` is `2.<count>` (2.x is the v2 redesign; 1.x, up to 1.61, was the original design), so every build from a newer commit installs as an update. Release builds are signed from a properties file **outside the repo**: `~/.android/watchlog-release.properties`, or the `WATCHLOG_SIGNING_PROPERTIES` env var, with `storeFile`/`storePassword`/`keyAlias`/`keyPassword`. Without it, release builds come out unsigned. Every build installed on the phone must use that same key, or Android refuses the update, and the only way out is uninstalling, which wipes the app's data. So never sign with a different key, and keep the keystore and passwords backed up. Debug builds use the machine's own debug key, so **don't install a debug build over the release-signed app**. **Releases:** users download the APK from GitHub Releases. The README's link is `releases/latest/download/Watchlog.apk`, so every release must attach the APK as exactly `Watchlog.apk`, tagged `v2.<commit count>` (steps in `docs/DEVELOPMENT.md`). The README is a non-technical user guide (install, TMDB token, usage, backups, troubleshooting); technical material belongs in `docs/DEVELOPMENT.md`.

**Capacitor version note:** pinned to Capacitor 6 (not the latest major) deliberately, for Node 18 compatibility and to pair with Gradle/AGP 8.2.1, built with JDK 17 — JDK 21 predates that AGP pairing's support window. Don't bump `@capacitor/*` without checking this still holds.

## Architecture

**Folder layout:** `public/` (the whole app, loaded into Capacitor's WebView — `styles/` and `scripts/` subfolders, HTML pages at its root), `android/` (the Capacitor-generated native wrapper — mostly generated/boilerplate). The hand-written parts are `AndroidManifest.xml`; `MainActivity.java` (native back-button handling, and registering the app's own plugin); `WatchlogBackgroundPlugin.java` + `EpisodeCheckWorker.java` (the daily background episode check, see the notifications section); and `app/build.gradle`'s versioning and release signing. `docs/icons/` holds Material Symbols SVGs left over from the v1 design (the app's icons now come from the design system, `media.js`'s `ttIcon`) — not loaded by the app — plus `watchlog-launcher.svg`, the source artwork for the app icon.

**Name, IDs and app icon.** The display name is **Watchlog**: `capacitor.config.json`'s `appName`, `android/app/src/main/res/values/strings.xml` (`app_name`/`title_activity_main`), page text and README. Some identifiers deliberately still say `tvtimeclone`, and must not be renamed. The Android application id `com.tvtimeclone.app` (`appId`, `strings.xml`'s `package_name`/`custom_url_scheme`, the Java package): changing it makes Android treat the build as a different app, so installs no longer update in place and data is lost without a backup restore. The backup format id (`app: 'tvtimeclone'` in `backup.js`): every existing backup file carries it. The launcher icon (episodes as bars, the latest one ticked) is an adaptive icon: `res/mipmap-anydpi-v26/ic_launcher{,_round}.xml` → `res/drawable/ic_launcher_foreground.xml` (a vector, scaled to stay inside the 66dp safe zone) on `@color/ic_launcher_background` (`#5E63FF`, the v1 design's accent; the in-app accent is now chosen in Settings). Pre-Android-8 devices use the `res/mipmap-*/ic_launcher{,_round}.png` files, rendered from the same shapes. Changing the artwork means updating the SVG, the vector and those PNGs together.

**No backend — a fetch shim replaces the server.** `public/scripts/localApi.js` monkey-patches `window.fetch` and intercepts every `fetch('/api/...')` call the app already makes, so none of the ~49 existing call sites across the app needed to change when the server was removed. It must be the **first** script tag on every page (before `profiles.js`/`auth.js`), so the patch is installed before any page-load-time fetch fires. Two kinds of routes:
- `/api/tmdb/*` — passed straight through to `https://api.themoviedb.org/3/*`, injecting the active profile's own API key as a bearer token (TMDB sends `access-control-allow-origin: *`, so this works from a WebView/browser with no server in between).
- Everything else (`/api/lists/*`, `/api/watched/*`, `/api/favorites/*`, `/api/stats`, `/api/recommendations/*`) — handled locally via `route(method, pattern, handler)`/`matchPath()`/`dispatchLocalApi()`, reading/writing the active profile's IndexedDB. Response shapes are identical to the old server API, so `media.js`, `detail.js`, etc. don't know the difference.

**Every actual TMDB network call funnels through two chokepoints** (`handleTmdbPassthrough` for the `/api/tmdb/*` route, `fetchLocalTmdb` for the local routes' own server-side-style enrichment) — fixing something at either point automatically covers every caller, without touching individual routes/pages:
- `queueTmdbRequest` caps real concurrent requests at `TMDB_MAX_CONCURRENT` (20) and gives every request a `TMDB_TIMEOUT_MS` (10s) timeout. Without this, a page that enriches many items at once (Profile's Watched/Favorites sections especially, one TMDB request per item) fires dozens of simultaneous requests, which is slow enough on a phone's real network to look stuck and/or trips TMDB's abuse-rate limiting.
- `fetchLocalTmdb` retries transient failures (429/5xx/timeout, not 404/401) up to `TMDB_MAX_RETRIES` times with a short backoff — previously any transient failure permanently fell back to a blank "Unknown" card (no poster/title/rating) with no retry.
- `inFlightTmdbRequests` shares one in-flight promise across simultaneous callers requesting the exact same path (e.g. `/api/stats` and `/api/watched/movies/details` both wanting the same just-watched movie's `/movie/{id}` at once) instead of each firing its own request.
- `/movie/{id}` and `/tv/{id}` responses specifically (not sub-resources like season data, which needs to stay fresh for new-episode detection) are cached in IndexedDB's `tmdb_cache` store for `TMDB_DETAIL_CACHE_TTL_MS` (7 days) — a movie's runtime or a show's episode count barely ever changes, so once fetched once it's an instant local read on every subsequent lookup, across routes and across page loads, instead of a repeat network round trip.
- `stripAdultItems` filters TMDB's `adult: true`-flagged results out of every `results`/`parts` array (search, discover, trending, recommendations, collection parts) — that flag marks actual pornographic content specifically, not general R-rated mainstream movies/shows, so this doesn't affect legitimate mature content. `cast`/`crew` arrays are filtered only for entries that carry a `media_type`, meaning a person's `/combined_credits` (real movie/show objects with a real adult flag). They're left alone on a movie/show's own `credits`, where each entry is a person whose `adult` field means something different (their own known-for work) and stripping them would incorrectly drop real cast/crew credits.

**Show status** (`localApi.js`'s `computeShowStatus`, returned by `GET /api/watched/shows?includeStatus=true` as `status`/`airedCount`/`unwatchedCount`):
- `watching`: has aired episodes you haven't watched, and isn't dropped.
- `caught_up`: every aired episode watched, show still running.
- `completed`: every episode watched and TMDB's `status` is `Ended`/`Canceled`.
- `dropped`: unwatched aired episodes, and nothing watched for 30+ days (`SHOW_DROP_AFTER_MS`), counted from whichever is later — the last watched episode or the release of the oldest unwatched one. So a show returning from a break gets a fresh 30 days.
- `unknown`: the TMDB lookup failed.

"Aired" comes from `last_episode_to_air` plus each season's `episode_count` (`airedEpisodeKeys`), with specials excluded and no season fetches. The one season fetch, for the oldest unwatched episode's air date, only happens for shows not watched in 30+ days. These rules were decided with the user:
- Keep Watching (`shows.js`) and Home's Continue Watching (`app.js`, the three most recently watched, each with its next unwatched episode from `computeShowStatus`'s `nextUnwatched`) show only `watching`. Caught-up shows on a break are left out, and appear in Airing Soon once a date is announced.
- Dropped shows leave Keep Watching but stay in Airing Soon and still get notifications.
- The watched-shows list (`media-list.html?source=watched&type=tv`, `media-list.js`) shows each show as a progress row (`media.js`'s `buildShowProgressRow`: poster, status pill, progress bar through aired episodes), not a poster grid, with a BrowseHeader whose sheet has a Status filter (All / Watching / Caught up / Completed / Dropped, `?filter=`) and the usual sort menu. The old `?source=in-progress` link maps to `filter=watching`.

**Airing Soon page** (`airing-soon.html`/`airing-soon.js`, opened from "See all" on Home's Airing Soon, which shows the next three): a horizontally scrolling week strip in the sticky header (today onward, at least 14 days, up to 120; days with episodes show a count and jump to that day in the list), then every announced upcoming episode in date order as airing rows (date tile, show, episode, "Today"/"In 3 days"). The date tile (`media.js`'s `buildAiringRow`, also on Home) shows just "TODAY" (no number) on the day itself, the weekday ("WED 6") only when the episode is within the next 7 days, and the month ("JAN 6") further out, so a far-off date can't be read as this week (decided with the user). Data: `GET /api/watched/shows/schedule`, which takes each tracked show's `next_episode_to_air` season plus later seasons and returns every episode airing today or later, dropped shows included. If TMDB's season list doesn't have the next episode yet, it falls back to `next_episode_to_air` itself.

**Stats page** (`stats.html`/`stats.js`, "User Statistics", opened from "See all" on Profile's Stats; the summary tiles are shared via `media.js`'s `renderStatTiles`, five tiles on both, `layout: 'profile'` or `'stats'` only changes the order). Each section loads separately:
- the summary tiles (`/api/stats`)
- watch time per month for the last 12 months, plus top genres by number of watched titles (`/api/stats/details`)
- top actors (`/api/stats/actors`): top-billed cast only, TMDB `order` < 10, counted once per title from `/movie/{id}/credits` and `/tv/{id}/aggregate_credits`, which the detail cache also stores

Per-show progress used to be a Stats section; it moved to the watched shows list (decided with the user).

**Preview sections cap how much they enrich, not just how much they render.** Profile's Watched/Favorites rows and `shows.js`'s Keep Watching row only ever display a fixed number of items (`WATCHED_PREVIEW_LIMIT`/`KEEP_WATCHING_PREVIEW_LIMIT`, both 8 — smaller than the 20 the TMDB-list-backed rows show, since on a cold cache each visible item here can cost its own TMDB round trip), but naively fetching the full list and truncating client-side still means enriching a profile's *entire* watched/favorites history just to show 8 of them. `/api/watched/movies/details`, `/api/watched/shows`, `/api/favorites/movies`, and `/api/favorites/tv` instead accept an optional `?limit=` that slices the raw rows down *before* enriching (`applyLimit` helper). Profile's four sections request exactly `?limit=8` (each section's header has a "See all" link), while `media-list.html`'s "see all" page calls the same endpoints with no `limit`, since it needs the true full list. Keep Watching is the exception: it fetches `/api/watched/shows?includeNewEpisodes=true` unlimited and only caps what it *renders*, since it has to check every tracked show's progress before it knows which ones are in progress. `/api/stats` is deliberately never limited either, since it needs accurate totals (e.g. total watch time) across everything, not a sample.

**Watched movies and favorites store their own display fields (denormalized at write time).** When a card's watched/favorite button fires, the client already holds the item's standard shape, so `media.js` sends `pickSummaryFields(item)` (title/year/releaseDate/posterPath/voteAverage) in the POST body and `localApi.js` writes them onto the `watched_movies`/`favorites` row. Reading those lists back (`summaryFromRowOrFetch`) is then a pure IndexedDB read with zero TMDB calls. Rows without them (written before this existed, or by the since-removed TV Time importer, which POSTed with no body) fall back to one live fetch and get backfilled. A failed fetch's "Unknown" placeholder is deliberately *not* persisted, so it stays retryable. Watched *shows* aren't denormalized this way: they need a live `/tv/{id}` anyway for episode count/progress, so it would save nothing.

**Skeleton loading:** `media.js`'s `buildSkeletonCard()`/`renderSkeletonRow(container, count)` render shimmering placeholder posters with the real `.tt-poster` structure, so nothing reflows when real cards replace them; `buildSkeletonMediaRow()` is the same for row lists (Continue Watching, Airing Soon, search results, the watched shows list). `loadPosterRow` shows them while it loads. Every row or grid that waits on a network fetch uses them, and a new network-backed one should too.

**Per-profile preferences and Settings.** `settings.html`/`settings.js`, opened from the ⋯ on Profile's card. Preferences live on the profile's registry entry (`prefs`), read with `getProfilePrefs()` (merged over `PROFILE_PREF_DEFAULTS`) and written with `setProfilePrefs(id, updates)`, both in `profiles.js`: `theme` (dark/light/system), `accent` (one of `ACCENT_COLOURS`), `region` (null = guess from the locale; `profileRegion()`), `language` (TMDB language tag; `profileLanguage()`), `notifyEpisodes`/`releaseReminders`/`weeklyRecap`, `autoBackup`. `theme.js` is a plain non-deferred script right after the stylesheets on every page: it reads the active profile's prefs straight from localStorage and sets `data-theme` and the `--accent*` variables on `<html>` before paint (`window.applyProfileTheme()` re-applies after a change). Settings also edits the name and TMDB token (validated when changed), picks region and language from TMDB's `/configuration/countries` and `/configuration/primary_translations` (searchable lists), and has Back up now, Export/Import data, Switch profile, Delete profile, Reset all data (`POST /api/reset`: empties the library stores and recreates an empty Watchlist; keeps the profile, token, settings and TMDB cache), Licences (`licences.html`) and the installed version (`WatchlogBackgroundPlugin.getAppInfo`).

**Language and region in TMDB requests.** `localApi.js`'s `localizeTmdbPath` (applied in both chokepoints) replaces `language=` with the profile's language for anything but English, and widens `include_video_language` when videos are requested so trailers still turn up. English profiles' URLs are unchanged. The detail cache key gets an `@<language>` suffix for non-English profiles. TMDB leaves a field empty when it has no translation, so the detail and person pages append `translations` for non-English profiles (`media.js`'s `withTranslations()`) and fall back to the English overview/biography (`textOrEnglish()`). `media.js`'s `getUserRegion()` returns `profileRegion()`.

**Local profiles replace server accounts.** `public/scripts/profiles.js` is a small registry in `localStorage` (`tvtc_profiles` key: `[{id, displayName, tmdbApiKey, createdAt}]`, `tvtc_active_profile_id` key: which one is active) — this registry only holds identity, not app data. `public/scripts/auth.js` keeps its old function names (`getCurrentUser`, `requireLogin`, `logout`) so every existing call site (`bookmarks.js`, `detail.js`, `lists.js`, `media.js`, `profile.js`, `media-list.js`) is unchanged; only what backs them did — `getCurrentUser()` now resolves to the active local profile, `requireLogin()` redirects to `profile-picker.html` (not `login.html`, which no longer exists) if none is active. `public/index.html` is the real entry point (`webDir` in `capacitor.config.json`): it redirects to `main.html` or `profile-picker.html` depending on whether a profile is active.

**Each profile gets its own IndexedDB database**, not one shared database with a profile-id column: `public/scripts/localDb.js` opens `tvtc-profile-{profileId}`, object stores mirroring the old `server/schema.sql` tables minus the `user_id` column (the whole database *is* one profile's data) with JS-camelCase field names. This is deliberate: it keeps each profile's data trivially exportable/deletable as one unit (`indexedDB.deleteDatabase(...)` in `profiles.js`'s `deleteProfile`) and keeps the privacy blast radius of a bug contained to one profile rather than every profile sharing one store.

**TMDB API key handling:** entered per profile on `profile-picker.html` (create, edit, or when restoring a backup) or changed in Settings (the profile card or Account > TMDB token), stored in plaintext in `localStorage`. That's acceptable for a single-device offline app (it's inside the app's own sandbox), but worth remembering if adding any profile-sharing/sync feature later. The "key" is TMDB's long **API Read Access Token**, sent as a bearer token; the short 32-character v3 "API Key" doesn't work that way. `profiles.js`'s `validateTmdbApiKey()` checks it against TMDB's `/authentication` before saving (only when the key is new or changed) and returns a specific message for a rejected token, a short v3 key pasted by mistake, or no network.

**Backup/restore** (`public/scripts/backup.js`) exports a profile's full IndexedDB data (not `tmdb_cache`) as a JSON file and restores one into a **new** profile, never overwriting an existing one. Backups **never contain the TMDB key** (format `backupVersion: 2`): the files end up in shared places (public Documents, Drive, email), and the key is free to re-obtain. Restoring on `profile-picker.html` opens the profile form in restore mode, asking for a key, validating it, then calling `restoreBackup()`. Settings' "Import data" asks how to load it (`settings.js`'s `importChoiceDialog`, decided with the user): **merge** into this profile or **replace** its library (`backup.js`'s `importBackupIntoProfile(profile, payload, { mode })`: replace runs `POST /api/reset` first; merge keeps the more recent of watched movies/episodes/favourites/list items by `watchedAt`/`favoritedAt`/`addedAt`, matches lists by sync id then name ignoring case (a clash with a name gets " (2)"), puts the backup's Watchlist into this one, prunes watched titles off the Watchlist, and on an online profile records every change for sync, with tombstones for Watchlist items the prune removed; tests in `tests/sync.test.js`), or as a new profile (`restoreBackup`, reusing the current profile's key). Old `backupVersion: 1` files did embed the key; they still restore, and `legacyBackupApiKey()` offers that key as a prefill. Manual export (Settings > "Export data") branches on `isNativeApp()`: the native Share sheet on Android, a plain blob download on the web. Vendored Capacitor plugins (Filesystem, Share, LocalNotifications) live as plain `<script>` tags in `public/scripts/vendor/`, copied from each package's `dist/plugin.js`, since there's no bundler to import them.

**The web app (PWA).** The same `public/` is published on Cloudflare (a static-assets Worker named `watchlog`, `wrangler.jsonc`; live at https://watchlogtracker.com, a Custom Domain of the Worker with `www.` redirected to it by a zone Redirect Rule; deployed from `main`, with a preview deploy per branch on workers.dev; `docs/DEVELOPMENT.md`, "The domain") as an installable web app, which is how the app runs on iPhone (Safari > Add to Home Screen); setup is in `docs/DEVELOPMENT.md`'s "The web app". Pieces:
- `manifest.webmanifest` plus icons in `public/images/` (`icon-192/512.png` rounded, `icon-maskable-512.png` and `apple-touch-icon.png` full-square, `icon.svg`, all rendered from `docs/icons/watchlog-launcher.svg`). Every page has the same head block: `theme-color`, the `apple-mobile-web-app-*` tags (status bar `default`), the manifest, icons, and `viewport-fit=cover`.
- `sw.js` is network first with a 4 s timeout, then the cache, for this origin's files only (not TMDB). Cache keys drop `.html` and the query string (`cacheKey`), because Cloudflare's static assets redirect `page.html` to `/page`; redirected responses are re-wrapped before caching. Its `PRECACHE` must list every file in `public/` (`tests/pwa.test.js` checks), so **add new pages, scripts and images to it**. `version.json` is never cached.
- `scripts/pwa.js` (every page but `index.html`, deferred, right after `theme.js`) registers `sw.js` and calls `navigator.storage.persist()`. It returns immediately in the Android app.
- `theme.js` writes the theme's `--bg-surface` into `meta[name=theme-color]` (the installed app's status bar). Layout CSS (`.screen`, `.page-header`, `.detail-hero`, `.picker`, `.tt-nav`) pads with `env(safe-area-inset-*)`, which is 0 outside a full-screen iPhone app.
- Backups on the web: no auto-backup. `backup.js`'s `exportBackup` uses the share sheet on touch devices (`shareBackupOnWeb`: `navigator.share` with a file; falls back to a download when the browser can't share the file, and saves nothing if the person cancels), a download on desktop, and returns false when cancelled. Each export is recorded (`recordBackupExport`, localStorage `tvtc_backup_exports`), and Profile's backup row (`renderWebBackupReminder`) warns when there's no export or it's `BACKUP_REMINDER_AFTER_DAYS` (7) old; Settings' Export row shows the last date.
- Version: `tools/write-web-version.js` (the Cloudflare build command) writes `public/version.json` (`2.<commit count>`, unshallowing the clone first, and the commit id from `git rev-parse HEAD`; Cloudflare's commit variables are only a fallback, since a Workers build's held the branch name); gitignored. Settings' `webVersionLabel` reads it, else "web preview".
- Notifications on the web come from the server, for online accounts only ("Server notifications" below).

**The server (roadmap Phase 2; nothing in the app calls it yet).** The same `watchlog` Worker runs `server/src/index.js` (`wrangler.jsonc` `main`), plain ES modules with no dependencies (`server/package.json` is `"type": "module"`). Static files are served first; the script only runs when no file matches: `/v1/...` → `api.js`, anything else → `env.ASSETS.fetch` (404). Decisions:
- The API prefix is **`/v1/`**, never `/api/` (the client shim `localApi.js` owns `/api/` on the device). `sw.js` skips `/v1/` (tested in `tests/pwa.test.js`).
- `router.js`: `route(method, '/path/:param', handler)`, handlers get `{ request, env, ctx, params }` and return a Response (`json()`, `noContent()`, `apiError(status, code, message)`); `readJson(request)` parses a body (16 KB max); throw `ApiError(status, code, message, { retryAfter })` for an expected failure. Route modules live in `routes/` (`health.js`, `accounts.js`, `tmdb.js`, `sync.js`, `push.js`, `admin.js`) and are imported by `api.js` (kept apart from `router.js` to avoid a circular import). `api.js` handles CORS and turns errors into responses: `{ error, message }`; unexpected errors become a generic 500 and are logged (observability is on). Unknown path 404, wrong method 405. CORS: same origin always; other origins only from `ALLOWED_ORIGINS` (comma-separated var; `https://localhost` = the Android app); disallowed cross-origin requests get 403. `GET /v1/health` (`{ ok, environment, database, migration }`, 503 if D1 fails).
- TMDB proxy (`routes/tmdb.js`, Phase 5 pulled into Phase 3): `GET /v1/tmdb/*` for signed-in accounts, asks TMDB with the `TMDB_TOKEN` Worker secret (dashboard, Production and Previews Base tabs; never in the repo). Read-only paths only (`BLOCKED`), body passed through unparsed, TMDB 401 → our `503 tmdb_unavailable`, 429 → `503 tmdb_busy`, other statuses pass through. Daily D1 counters `tmdb:account:<id>` (5,000) and `tmdb:all` (40,000) (`TMDB_LIMITS`). `TMDB_PROXY` var `"off"` pauses it. Edge cache via `caches.default` when present (`cacheSeconds`), keyed by the TMDB URL alone; it works on `workers.dev` (checked, `X-Watchlog-Cache: hit`), per data centre. Router patterns ending in `/*` capture the rest as `params.path`.
- Sync (Phase 4a, `routes/sync.js`; the app's side is `sync.js`, see "Sync in the app" below): `POST /v1/sync { since, changes }` → `{ cursor, changes, more, accepted, serverTime }`. Table `sync_records` (migration `0003_sync.sql`, PK account + `kind` + `record_key`, `data` JSON or NULL for a tombstone, `deleted`, `updated_at`, `seq`); `accounts.sync_seq` is bumped with `UPDATE ... RETURNING` to reserve a seq range per request, so concurrent syncs never share numbers. Newest `updated_at` wins (an upsert with `WHERE excluded.updated_at > sync_records.updated_at`; ties keep what's stored); device times are capped at server time + 5 min. Kinds: `SYNC_KINDS`. Limits: `MAX_CHANGES_IN` 200 per request, `MAX_CHANGES_OUT` 500 per reply (`more`), 128 KB bodies (`readJson(request, { maxBytes })`), 2 KB per record, `SYNC_LIMIT` 600/hour per account.
- Accounts (Phase 3a, `routes/accounts.js` + `auth.js`; used by the app since 3b): account key = 27 Crockford base32 chars + a mod-31 weighted check char, 7 groups of 4 (`generateAccountKey`; `accountKeyData` normalizes O/0, I/L/1, case, spaces, dashes); stored as SHA-256 (`hashAccountKey`, namespaced like the other hashes). Session tokens: 32 random bytes, Bearer, stored hashed, 180 days idle expiry, `last_used_at` written at most hourly (`requireAuth`). Pairing codes: 8 chars, single use (claimed with `DELETE ... RETURNING`), 10 minutes, a new one cancels the old. Rate limits: fixed windows in the `rate_limits` table (`rateLimit`), keyed by a hash of `CF-Connecting-IP` (`clientKey`) or the account id; who may sign up is the admin page's sign-up mode (below), and creating accounts is limited per address and overall (`LIMITS`) whatever the mode. `requireAuth(request, env, { allowPending })`: an account's `status` is `active`, `pending` (refused with `403 account_pending` unless the route allows it: `GET`/`DELETE /account`, `DELETE /session`) or `suspended` (sessions deleted; signing in answers `403 account_suspended`). The route table is in `docs/DEVELOPMENT.md` ("Accounts API"). Tables (migration `0002_accounts.sql`): `accounts`, `sessions`, `pairing_codes` (cascade on account delete), `rate_limits`. The Sunday cron runs `cleanup.js` (expired sessions/codes, old counters) before the backup; a failing cleanup doesn't stop the backup.
- D1 binding `DB`: production database `watchlog`, previews `watchlog-preview` (the `previews` block; previews inherit nothing but assets/compatibility settings, so vars and bindings are repeated there). `wrangler.preview-db.jsonc` names the preview DB again, only for applying migrations to it; `tests/server-config.test.js` checks the two match, that previews never use the production DB, and that no `REPLACE_WITH_` placeholder is left.
- Migrations: numbered SQL files in `server/migrations/` (`0001_init.sql` only creates `app_meta`). Workers Builds runs `npm run cf:build` on every build (version.json + migrations to the **preview** DB), then `npm run cf:deploy` on `main` only (migrations to the **production** DB, then deploy); previews then run `npx wrangler preview`, so no preview build can touch production. Each preview copies Previews Base when first created and keeps its own build settings (on that preview's Settings page), so a Previews Base change doesn't reach existing previews. Never edit an applied migration; add a new one.
- Backups: D1 Time Travel (7 days on the free plan), plus a Cron Trigger (Sundays 03:00 UTC, not in previews) whose `scheduled` handler runs `backup.js`'s `runBackup`, writing the new copy to R2 binding `BACKUPS` first, then keeping the newest `BACKUPS_TO_KEEP` (5, decided with the user) of either kind. **Sync in the app** (roadmap Phase 4b, `public/scripts/sync.js`, loaded right after `serverApi.js` on every page that loads `localApi.js`, so not the picker). Only profiles with an `account` sync. Pieces:
- Records are `{ kind, key, data }` built by `syncRecordFor*` (`syncTombstone(kind, key)` for a deletion): `watched_movie` `550`, `watched_episode` `1399:1:1`, `favorite` `movie:550`, `list` (key = the list's `syncId`; the Watchlist itself is never a record), `list_item` `<list syncId>:<mediaType>:<tmdbId>`, `prefs` (`SYNCED_PREF_KEYS`: theme, accent, region, language; notification and auto-backup switches stay per device, decided with the user).
- **Every write in `localApi.js` must call `recordSyncChanges(db, [...])`** after it changes the library (including `removeFromWatchlist` and `/api/reset`, which records a deletion for everything). A new write route that forgets it won't sync. It's a no-op for offline profiles. Settings' `savePrefs` calls `recordPrefsChange`. Display-field backfills (`summaryFromRowOrFetch`) don't record.
- Database v5 (`localDb.js`): lists get `syncId` (unique index; `WATCHLIST_SYNC_ID` = `'watchlist'` for the Watchlist on every device, `newSyncId()` otherwise; `newWatchlistRow()` for new and reset databases), plus stores `sync_outbox` (keyPath `id` = `<kind>|<key>`, the newest waiting version of each record) and `sync_state` (`{ key: 'state', account, cursor, lastSyncAt, lastError }`). Restoring a backup gives lists without one a `syncId` (`ensureListSyncIds`) and lets the backup's Watchlist replace the new profile's empty one.
- `syncNow()` (one at a time per page): rounds of `POST /v1/sync` with up to 200 outbox rows (`takeSyncBatch`, also capped at 100 KB), applying incoming changes (`applyIncomingChanges`: lists first; skipped when the outbox has a newer change for that record, or the same time with different data, matching the server's tie rule), then clearing the rows that were sent unless they changed meanwhile. `state.account` is `<account id>@<linkedAt>`; when it doesn't match (the first sync, e.g. after "Make this an online account") `queueFullUpload` queues the whole library with each record's own time (prefs with the epoch, so the account's win).
- **Times come from the server's clock**: each sync reply has `serverTime`; `measureClockOffset` keeps the difference in `sync_state.clockOffsetMs`, and `recordSyncChanges` stamps changes with `syncTime(db)` (device clock + offset). So a device whose clock is wrong still has its newest change win. Before its first sync a device uses its own clock.
- Same-named lists: `applyListRecord` renames the later list (`createdAt`, then `syncId`) to "Name (2)" and records the rename, so every device converges. A list item whose list hasn't arrived yet goes on a stand-in list that the list's record updates.
- Triggers only in a real page (`syncAutoEnabled`; tests call `syncNow` directly): 800 ms after `load` (skipped if synced in the last 10 s, `SYNC_RECENT_MS`, with nothing waiting), 2 s after a change (`scheduleSync`), `online`, and visibility back to visible; `navigator.locks` keeps two tabs from syncing one profile together. After a sync that changed something (`showSyncedChanges`), a page the person hasn't touched yet (no pointerdown/keydown/wheel/touchstart) reloads itself, at most once per 15 s (sessionStorage `watchlog_sync_reloaded_at`); a touched page instead shows an "Updated from your other devices · Refresh" toast (`.sync-toast`, not on Settings), so nothing jumps under the person's finger (decided with the user). `SYNC_EVENT` (`watchlog-synced`) fires after every sync; Settings' Sync row (`getSyncStatus`) listens for it.
- Settings: the Online account section starts with Sync (status + Sync now). Reset all data on an online profile warns that it empties every device, and syncs before and after.
- Tests: `tests/sync.test.js` runs two harness pages (two devices) against an in-memory server with the real server's rules. The local Worker (`wrangler dev --local`, launch config `watchlog-worker`, after `npx wrangler d1 migrations apply DB --local`) runs it all on this machine; two profiles in one browser signed in to the same account act as two devices.

**Weekly auto-backup** (`public/scripts/autoBackup.js`, Android only). There's no background job: a few seconds after any page loads, `runAutoBackups()` checks each profile on the device, and for any whose last auto-backup is 7+ days old, writes the same backup JSON to public `Documents/Watchlog/watchlog-<name>-<YYYY-MM-DD>.json`. That folder survives uninstalling the app; IndexedDB doesn't. One file per profile is kept: the new one is written **first**, then the previous one is deleted, so a failed write never leaves zero backups. Android 11+ lets the app write and delete its *own* files there without a storage permission (the Filesystem plugin skips the permission check on API 30+), but not files a previous install created. A failed delete is recorded in `undeleted`, retried on the next run, and shown in the status row on the Profile page. Settings > Auto-backup switches it off per profile (`autoBackup` pref): `runAutoBackups` then skips that profile, except for an explicit "Back up now" (`force: true`). State is per profile in localStorage `tvtc_auto_backup` (`{ path, savedAt, undeleted, lastError }`). Settings has "Back up now" (`force: true`); Profile shows the status. **Online profiles never auto-back up** (decided with the user: their library is saved to the account): `runAutoBackups` skips any profile with an `account`, even when forced; Settings shows the switch off and disabled ("Not needed: your library is saved to your online account") and hides Back up now; Profile's status row says "Saved to your online account" (or warns while signed out), and the web export reminder isn't shown for them. Export data still works for everyone.

**Notifications** (`public/scripts/notifications.js`, Android only, `@capacitor/local-notifications`). Three kinds, each a per-profile switch in Settings (`notifyEpisodes`, `releaseReminders`, `weeklyRecap` prefs); `refreshEpisodeNotifications` schedules all the enabled ones in one run (status `disabled` only when all three are off):
- **Release reminders:** `GET /api/watchlist/releases` lists Watchlist movies with a release date today or later in the profile's region (`regionalReleaseDate`: earliest theatrical date, types 2/3, else digital, type 4, from `/movie/{id}/release_dates`; movies with neither for the region are skipped). One notification per movie at 18:00 on that date, id `episodeNotificationId('movie', id, date)`, opening the movie.
- **Weekly recap:** next Sunday 19:00 (`nextRecapTime`), body from `GET /api/recap?at=` (episodes/movies watched in the 7 days before, their watch time, episodes airing in the 7 days after). It's written when scheduled, so it reflects what was watched up to the last app open before Sunday evening. Fixed id `RECAP_NOTIFICATION_ID`, opens Stats.
- **New episodes**, as follows.

New-episode notifications: There's no server or push: on page load (throttled to every 6 h per profile, or immediately after a profile switch or a settings toggle), `refreshEpisodeNotifications()` takes `GET /api/watched/shows/upcoming` for the **active** profile and schedules one local notification per show, at `EPISODE_NOTIFY_HOUR` (18:00) local time on its air date. Notification id = the show's TMDB id, and all pending ones are cancelled and rescheduled on each run. Android fires them with the app closed, and the plugin restores them after a reboot. Only each show's *next* episode is known, so the one after it is scheduled on a later app open. Notification ids are **per episode** (`episodeNotificationId`: Java's `String.hashCode` of `showId:season:episode`, masked to 31 bits). That means an episode is never scheduled twice, and rescheduling never replaces a notification that already fired. Tapping a notification opens `extra.url` (release reminders, recap) or `detail.html?type=tv&id=` (from `extra.showId`): every page registers the listener, and the plugin holds the event until one exists.

**Daily background check** (so a show's following episode gets scheduled without opening the app). `WatchlogBackgroundPlugin.java` (a Capacitor plugin registered in `MainActivity`, reached from JS via `capacitorExports.registerPlugin('WatchlogBackground')`) has `configure({ enabled, apiKey, notifyHour, smallIcon, shows })`. `notifications.js`'s `syncBackgroundEpisodeCheck` calls it after every refresh: with the active profile's key and every tracked show when scheduling, or `enabled: false` when off, refused, or no profile. It stores that in private SharedPreferences (`watchlog_background`), and keeps a 24-hour WorkManager job (`EpisodeCheckWorker`, network required) scheduled or cancels it. The worker fetches `/tv/{id}` for each show and schedules any future next episode that isn't already pending. It does this through the local-notifications plugin's own `LocalNotificationManager` + `NotificationStorage` (exactly what that plugin's reboot receiver does), so its notifications are identical to the app's: same icon, same tap handling, visible to `getPending`/`cancel`. It only ever adds; turning notifications off cancels everything from JS. `runNow()` triggers one check immediately, for testing. The worker can't read IndexedDB, which is why weekly backups still only run when the app is opened (agreed with the user). Permission (Android 13+) is requested on the first run; if refused, nothing is scheduled and the app doesn't re-prompt. The on/off switches are in Settings (per profile; the old device-wide `tvtc_notifications_enabled` key is only the default for profiles that never set their own). The background check is only enabled while new-episode notifications are on. `profile-picker.html` loads it only to clear notifications when no profile is active. The status-bar icon is `android/app/src/main/res/drawable/ic_stat_tvtc.xml`, configured in `capacitor.config.json`'s `LocalNotifications.smallIcon`. Because `/tv/{id}` responses are cached for 7 days, `localApi.js`'s `isTmdbDetailCacheEntryFresh` treats a cached show whose `next_episode_to_air` date has passed as expired, so Airing Soon and notifications learn about the following episode right away.

**Frontend has no bundler, so shared code is shared `<script>` includes, and load order matters.** The working convention is `standardItem.js` → `localDb.js` → `localApi.js` → `profiles.js` → `auth.js` → `media.js` → (`search.js` on pages with the typeahead search field: Home, Movies, Shows) → (`browse.js` on Movies/Shows) → page-specific script (`app.js`, `bookmarks.js`, `lists.js`, `profile.js`, `settings.js`, `detail.js`, `episodes.js`, `movies.js`, `shows.js`, `search-results.js`, `media-list.js`, `person.js`, `stats.js`, `airing-soon.js`). `standardItem.js` goes first because both `localApi.js` and `media.js` use it. It makes no fetches, so it doesn't break the rule that `localApi.js` patches fetch before anything fetches. Every page loads `theme.js` (non-deferred) right after the stylesheets, then `pwa.js` (deferred; not on `index.html`). Every sidebar page also loads the vendored Capacitor scripts (`vendor/capacitor.js`, `capacitor-filesystem.js`, `capacitor-local-notifications.js`, plus `capacitor-share.js` on `settings.html`) as plain non-deferred tags before everything else, and `backup.js` → `autoBackup.js` → `notifications.js` right after `profiles.js`. Every page that loads `localApi.js` also loads `serverApi.js` right after `profiles.js` (the TMDB proxy for online profiles), then `sync.js`. On the web these load harmlessly, and `isNativeApp()`/`notificationsSupported()` keep them inert. `profile-picker.html` is the one page that doesn't follow this. It has no sidebar, so it only loads `vendor/capacitor.js` + `capacitor-filesystem.js` + `capacitor-share.js` (saving the account key on Android) + `capacitor-local-notifications.js` → `localDb.js` → `profiles.js` → `serverApi.js` → `media.js` (for `ttIcon`/`buildTextField`/`confirmDialog`; it's safe without the other scripts) → `notifications.js` → `backup.js` → `profile-picker.js`. `media.js` is the shared component library; pages build their UI from it rather than writing their own markup:
- `buildCard(item)` builds the poster card (`.tt-poster`: art, then a "2026 • 8.4/10" meta line - "Not rated"/"Coming soon" when there's no rating or it isn't out - then the title), wiring in click-through to `detail.html?type=&id=`. `card.overlayActionsEl` is the art (toggles go on it), and `addCardDetail(card, text)` adds a line under the title ("3/10 episodes watched").
- `attachStandardActions(card, item, context, opts)` is the standard entry point every page calls to wire up the save/favorite/watched toggles on a card — don't reimplement these per page. The `attach*Button` helpers also take `{ button }` so the detail page can drive its own round icon buttons with the same logic.
- `fetchStandardActionContext()` batch-fetches the current profile's watched-movie ids, favourite ids and Watchlist contents (`watchlistKeys`, `watchlistId`) once per page load, so individual card buttons don't each fire their own request. The bookmark toggle is shown filled while the item is on the Watchlist.
- `renderBottomNav(nav)` fills every page's empty `<nav class="tt-nav" data-active="home|watchlist|lists|movies|shows|profile">` (automatically on DOMContentLoaded; call it again after changing `data-active`, as detail/media-list do; an empty `data-active` highlights no tab, as on the actor and search pages). Any element with `data-back="<fallback page>"` becomes a back button (history back, else the fallback, read at click time).
- `loadPosterRow(container, fetchPage, renderItem, opts)` fills a horizontal `.poster-row` from a paged feed (`fetchPage(page)` resolves to `{results, total_pages}`; `renderItem(raw)` builds a card or returns falsy to skip). If `renderItem` filters out results, it keeps pulling pages until it has `target` (20) cards, so a heavily-filtered row (Coming Soon) isn't sparse. Rows don't load more inline: their header's "See all" opens the full feed in `media-list.html`.
- `renderPagination(container, currentPage, totalPages, onPageChange)` is the shared round Prev / "Page X of Y" / Next pager used by browse grids, search, filmography and see-all feeds. Always exactly three elements, so it fits one phone-width line.
- Smaller builders: `buildPosterArt` (image, or the title's initials when there's no poster), `buildMediaRow` (thumbnail + title + meta + optional progress; search results, Continue Watching), `buildShowProgressRow` (the watched shows list), `buildAiringRow`, `buildCastCard`, `buildChip` (slim pills, only for in-place choices like Settings' theme), `buildTextField` (the design's TextField: label with an optional `aside` link, 48px box with a leading icon, show/hide for `type: 'password'`, helper/`setError()`; used by the picker, `promptDialog` and Settings' profile dialog), `createBrowseHeader` (see below), `buildProgressBar`, `buildStatTile`, `ttIcon(name, { filled })` (the design system's line icons), and `confirmDialog`/`promptDialog` (Promise-based dialogs used instead of `window.confirm`/`alert`).
- `renderSearchResultRows(resultsEl, rawResults, onSelect, { includePersons })` renders search results as media rows - `search.js`'s typeahead (with people) and the see-all page's "Add a title" dialog (movies/shows only, `onSelect` adds to the list).
- `normalizeTmdbPerson(raw)`/`personUrl(item)`/`buildPersonCard(person)` are the person (actor/crew) counterparts. A person is deliberately *not* forced into the standard item shape: it has no releaseDate/voteAverage, and its image is a profile photo, not a poster.

Adding a new page that lists movies/shows should reuse `buildCard`/`attachStandardActions`, not duplicate card-rendering logic.

**Design system (v2).** The look comes from the TV Tracker design system, kept in `docs/design/` (`tokens.json`, and `bundle.css`, the reference component CSS). `public/styles/tokens.css` is its tokens as CSS variables (dark theme, burgundy accent by default; the light set is there too) and must load before `style.css`, which holds the components (`tt-*` classes, matching `bundle.css`), the layout and each screen's pieces. Use the tokens (`--bg-card`, `--text-secondary`, `--accent-text`, `--radius-md`, `--space-4`, ...) rather than literal colours or sizes. The design's own rules: `--accent` is for fills (primary buttons, selected chips), `--accent-text` for accent-coloured text and on-poster toggles, `--accent-mark` for marks drawn on the page (active nav icon, progress bars, chart bars). **Filtering and sorting never get a row of chips** (the design's rule): every browsable list uses `media.js`'s `createBrowseHeader({ title, sortOptions, sections, values, summary, onChange })`, the design's BrowseHeader - an optional title, a one-line summary of what's applied, a sort icon (a small menu, applies at once) and a filter icon (a bottom sheet: `single` sections are a segmented bar whose first option means "no filter", `multi` sections a two-column checklist; "Show results" applies; an `--accent-mark` dot shows active filters). It returns `{ el, update(next), state }`; the sheet is drawn in its own layer on `<body>` so a sticky header can't trap it under the bottom nav. Used by Browse All (sort + genres), the see-all page (sort, plus Status for watched shows), search results (Show: All / Shows / Movies / People with counts) and the actor filmography (All / Movies / Shows with counts). Chips stay only for in-place choices that aren't filters. The design's browser layout is built for laptops only (see "Phone layout everywhere, plus a laptop layout" below). Screens: titled pages (`.screen` + `.screen-title`) for tab roots; a sticky `.page-header` (back button, title, BrowseHeader) for sub-pages (Search, Episodes, See all, Airing Soon); a full-bleed backdrop hero for detail and person. Copy follows the design: "Watchlist" (not Bookmarks), "Favourites", sentence-case buttons.

**Card action layout:** the toggles are round buttons on the poster art (`card.overlayActionsEl`), pinned to corners with `.pos-tr/-bl/-br/-tl`: eye (watched, movies only) top-right, heart (favourite) bottom-left, bookmark (save) bottom-right. List pages' remove × (`attachRemoveButton`) takes the remaining top-left corner. A toggle that's on shows its icon filled, in `--accent-text`.

**Card sizes:** posters in rows are 132px wide (`.tt-poster`, 2:3 art); in `.poster-grid` (three columns) they take the column width. Rows (`.poster-row`) scroll horizontally edge to edge and align items to the top, so a card with an extra detail line never stretches its neighbours.

**Watched tracking has two different shapes on purpose.** Movies are a single boolean (`watched_movies` store). TV is tracked per episode (`watched_episodes`, one row per show/season/episode) because per-episode progress is the core feature — there's no cached progress counter; "X/Y watched" is always computed live by combining the local watched count with TMDB's `number_of_episodes`. The show's detail page lists seasons as rows ("4/9 watched", ticked when complete); each opens **`episodes.html?id=<tmdbId>&season=<n>`** (`episodes.js`): a sticky header with the season's progress, then an episode card per episode (still, number, title, air date and runtime, a clamped synopsis with Show more, and a watched toggle). Marking an episode watched offers a "catch up" dialog to bulk-mark every earlier unwatched episode across all prior seasons too.

**The Watchlist (formerly Bookmarks) is still stored as a list under the hood** — the one `lists` row per profile with `isDefault: true`, auto-created when a profile's database is first opened — but is treated as a separate concept in the UI: `lists.js`'s `fetchLists()` filters out the default list, so it never appears on `lists.html`, and `bookmarks.html` is its own page ("Watchlist": a count, a search field that filters it, and Movies (n) / Shows (n) rows). It still shows up first, as "Watchlist", in the "Save to a list" popover (`media.js`'s `attachSaveButton`) since that's how items get added to it. Don't add a parallel bookmarks store/API if extending this — the split is presentation-only. **Watched titles never stay on it** (decided with the user): `localApi.js` removes a movie when it's marked watched and a show when any episode is (`removeFromWatchlist`), `POST /api/lists/:id/items` refuses a watched title for the Watchlist with a 409 (`isTitleWatched`; custom lists are unaffected), and the membership route returns `watched` so the save popover shows the Watchlist row disabled ("Watched"). `localDb.js`'s `pruneWatchedFromWatchlist` sweeps the whole Watchlist once when a database upgrades to v4 and after every backup restore. On the page, `media.js`'s `announceTitleWatched` fires `TITLE_WATCHED_EVENT` when a movie is marked watched, so bookmark buttons unfill and the Watchlist page and its see-all page drop the card.

**Lists and the see-all page.** `lists.html` shows one row per list (its first three posters stacked, name, size) and a "New list" button (`promptDialog`). A list opens in `media-list.html?source=list&id=` - the same "See all" template every section header links to (`media-list.js`): a sticky header (back, title, count, and a BrowseHeader with the sort menu Recently added / A–Z / Rating) over a three-column grid. Sources: `watched`/`favorites` (`&type=`; watched shows add a Status filter), `list` (remove ×, an "Add a title" tile that searches TMDB, and a ⋯ menu to delete the list), and TMDB feeds `trending`/`popular`/`upcoming`/`recommended` (`&type=`) and `similar` (`&type=&id=`, a title's recommendations), paged with the pager and not sortable.

**There are no user ratings.** Rating titles yourself was removed (decided with the user): no rating widget, no `/api/ratings` routes, no average rating or rating spread in stats. The `ratings` IndexedDB store is deleted by the v3 upgrade in `localDb.js` (ratings people had given are gone), new backups don't include it, and old backups' `ratings` are ignored on restore. The only ratings shown are TMDB's own scores (cards' "8.4/10", the detail page's star, the see-all "Rating" sort); don't add a user-rating feature back without asking.

**`detail.html`/`detail.js` is the single content page for both movies and shows**, distinguished by a `?type=movie|tv&id=<tmdbId>` query string — there's no separate movie-detail vs show-detail template. Layout: backdrop hero with a back button, the poster overlapping it beside the title, "year • genre • runtime/seasons" and the TMDB rating; then round icon buttons (watched for movies, save, favourite) plus Trailer (YouTube) when there is one, the clamped overview, then Seasons (shows), Cast (a row; "See all" expands it), the movie's collection, and More Like This (movies, from `append_to_response=recommendations`). The bottom nav highlights Movies or Shows to match. Cast cards link through to **`person.html?id=<tmdbId>`** (`person.js`, the design's Actor board): back button, photo with the department above the name, birth date/age and birthplace; a biography clamped to 3 lines with Show more/less (shown only when the text is actually cut off; episode synopses use the same pattern); Known For (their 10 most-voted credits); and the filmography from `/person/{id}/combined_credits` (cast+crew deduped, newest release first with undated projects last, a BrowseHeader titled Filmography whose filter sheet picks All / Movies / Shows with counts, shows marked "TV", `FILMOGRAPHY_PAGE_SIZE` 12 per page). Person results also appear in search: the typeahead, and the search page's People filter.

**Search** (`search.html`/`search-results.js`, opened by pressing Enter in any search field): a sticky header with the field (results update as you type) and a BrowseHeader whose summary counts the results and whose filter sheet picks All / Shows / Movies / People (with the current page's counts), then media rows and the pager. Movies/Shows' search fields are scoped to that type (`data-search-type`, which `search.js` uses for the typeahead and passes on as `?type=`).

**Movies/Shows "Browse All"** (`browse.js`'s `initBrowse`): a BrowseHeader titled "Browse All Movies/Shows" (sort menu Popular / Top rated / Newest; a Genres checklist in the filter sheet, any of which match - TMDB `with_genres` joined with `|`; the section is added once `/genre/{type}/list` loads) over a three-column discover grid with the pager. Titles you've already watched are left out.

**The "standard item shape" has one definition: `public/scripts/standardItem.js`.** `{ tmdbId, mediaType, title, year, releaseDate, posterPath, voteAverage }` is what every page passes around for a movie/show. `toStandardItem(raw, mediaType?)` builds it from any TMDB movie/tv object. `mediaType` defaults to the raw object's `media_type`, which TMDB only sends on mixed-type endpoints (trending, multi-search, combined_credits), so single-type callers pass it explicitly. `unknownStandardItem()` is the failed-lookup placeholder, and `pickSummaryFields()` is the subset written onto watched/favorite rows. `localApi.js` (`summaryFromTmdbData`, recommendations), `media.js`, `detail.js` and every page script use these; don't add another mapping. This used to be four hand-synced copies.

**Unreleased-content gating** goes through the same file's `isUnreleased(dateStr, now?)`: a missing or future date means it can't be marked watched yet. Its users:
- `media.js`'s `attachWatchedButton` disables the watched toggle.
- `episodes.js`'s `buildEpisodeCard` disables it and shows "Coming soon".
- Coming Soon (`movies.js`'s row and the `upcoming` see-all feed) doesn't filter page by page any more: TMDB's `/movie/upcoming` is mostly already-released movies, which left see-all pages with 1-3 movies. `media.js`'s `fetchComingSoonPage` keeps TMDB's upcoming set (its `dates.maximum` window end) but asks `/discover/movie` for theatrical releases (`with_release_type=2|3`) in the profile's region from tomorrow to then, so every page is full and "not out yet" means in your region (decided with the user).
- `media.js`'s `ratingLabel` shows "Coming soon" instead of a rating.
- `localApi.js`'s new-episode check uses it to ignore unaired episodes.

Separately, the detail page's season rows aren't links when `episode_count === 0` (they say "Coming soon"), so a season with no episodes can't be opened.

**Recommendations** (`localApi.js`'s `GET /api/recommendations/:mediaType` route) are seed-based, not a raw TMDB passthrough: it seeds from the profile's 5 most-recently-touched watched/list items, fetches TMDB's `/recommendations` for each seed, merges and ranks by match count then popularity, and excludes anything already watched/listed or a seed itself. The seeding/ranking (the expensive part — one TMDB request per seed) only depends on watched/list state as of when it first runs, so the ranked pool is cached in memory per `mediaType` for the rest of the page's session (`recommendationPoolCache`) rather than redone on every paginated request; a fresh page load always starts over. `?page=` slices `REC_PAGE_SIZE` (20) items at a time off that cached pool. Powers the "Recommended" rows on `movies.html`/`shows.html` and their see-all pages.

**"Keep Watching" and "Airing Soon" rely on a bounded new-episode heuristic**, not a webhook/polling system: `localApi.js`'s `computeNewEpisodeSeasons` only checks seasons at or above the profile's highest-watched season, comparing episode air dates against `lastWatchedAt`. This feeds the "New" badge on `shows.js`'s Keep Watching cards, the "New" pills on the detail page's season rows and on episode cards, and (via `GET /api/watched/shows/upcoming`) the Home page's Airing Soon rows.

Also: `movies.js`/`shows.js`'s "Popular" rows use `discover/movie|tv?with_origin_country=<region>` (the profile's region, Settings > Region, else guessed from `navigator.language`, via `media.js`'s `getUserRegion()`) to bias results toward the user's locale.

**Online accounts in the app** (`public/scripts/serverApi.js`, loaded after `profiles.js` on the picker and Settings). An online profile is a normal profile with `account: { id, displayName, sessionId, sessionToken, accountKey, keySavedAt, linkedAt }` on its registry entry and usually `tmdbApiKey: null`; its library stays in its own IndexedDB as before, and `sync.js` keeps it in step with the account. **TMDB for online profiles goes through the server's proxy** (decided with the user: they use the owner's token): `localApi.js`'s `tmdbAccess(profile)` picks `${serverBaseUrl()}/v1/tmdb` + the session token for a signed-in online profile, else TMDB + the profile's own token, else nothing; both chokepoints use it, and a 401 from the proxy clears the session (`noteProxySignedOut`). So `serverApi.js` loads on every page that loads `localApi.js` (after `profiles.js`), and the Android background check gets `tmdbBaseUrl` + the session token the same way (`notifications.js` → `WatchlogBackgroundPlugin`/`EpisodeCheckWorker`, which build `<tmdbBaseUrl>/tv/<id>`; empty means TMDB). `accountKey` is only on a device that created or typed it (shown again via Settings → Account key); `sessionToken` becomes null when the server answers `signed_out` (`accountRequest`), so Settings offers to sign in again. Requests go to `serverBaseUrl()`: the page's own origin on the web (a preview talks to its own preview), `PRODUCTION_SERVER_URL` in the Android app, or localStorage `watchlog_server_url` if set. `serverRequest` turns every failure into a `ServerError` with a message to show as it is (`offline`, `unavailable` for a non-JSON reply, the server's own messages, a wait hint on 429). `guessDeviceName()` names the device for the device list ("iPhone (web app)", "Android app", "Chrome on Windows"). Signing out or deleting the account asks (decided with the user) **Keep a copy** (the profile becomes offline with its library; if it has no token of its own, Settings sends it to the picker's offline form with a notice to add one) or **Remove it** (deletes the profile and its database: shared computers). A kept copy is an ordinary offline profile from then on (`unlinkProfileAccount` just clears `account`), and is never reattached: signing in again makes a new profile that starts from the account, so nothing done in the copy while signed out reaches the account (decided with the user). `profileForAccount` only finds a profile still linked to the account (one the server signed out), which gets the new session and keeps its outbox. Tapping a profile with neither a session nor a token in the picker opens the offline form to add a token. Deleting an online profile on this device signs its session out first. Settings' **Online account** section: Admin page (the owner only: `account.isAdmin`, with the waiting count), Sync, Account key, Make a new key, Add a device (a code dialog), Signed-in devices (sign others out), Sign out of this device, Delete online account; or "Make this an online account" for an offline profile.

## Testing

Run with `npm test` (`node --test tests/`, no framework, Node 18+). `tests/harness.js` loads the real `standardItem.js`/`localDb.js`/`localApi.js`/`profiles.js`/`backup.js`/`autoBackup.js`/`notifications.js` into a Node `vm` context that stands in for one browser page. It provides `fake-indexeddb` (the only dev dependency the tests need), an in-memory `localStorage`, and a fake TMDB server keyed by path, then drives the page through the shimmed `fetch('/api/...')` exactly like the app does. So the tests exercise the real route handlers, not copies of them. Each `createApp()` is a fresh page load, with a fresh DB and fresh module state. `put()`/`getAll()` read and write IndexedDB directly, to set up state the routes can't produce (e.g. a `watchedAt` in the past). `call(fnName, ...args)` calls any page-level function and returns a plain copy of the result. `createApp({ native: true })` makes `Capacitor.isNativePlatform()` true and installs in-memory fakes of the Filesystem and LocalNotifications plugins (returned as `filesystem`/`notifications`; options can make deletes or writes fail, or deny notification permission), so auto-backup and notification logic run exactly as on the phone.

Covered: show status (watching/caught up/completed/dropped, including the 30-day rule), the schedule route, stats details/actors, lists, watched movies (including denormalize/backfill/limit), favorites, watched titles leaving the Watchlist (`tests/watchlist.test.js`: on watch, the 409, the v4 upgrade and restore sweep), the ratings store's removal (DB upgrade, old backups), stats, the new-episode heuristic, upcoming, recommendations ranking/seeding/paging/cache, the detail cache (including `next_episode_to_air` expiry) and in-flight dedup, retries, adult filtering, passthrough auth, backup export (no key)/restore/legacy files, auto-backup scheduling/replacement/failed deletes/failed writes, notification scheduling/throttling/permission/disable, per-episode notification ids (matching Java's hash), the background-check sync (`createApp({ native: true })` also fakes the `WatchlogBackground` plugin as `background`), TMDB key validation, and Settings (`tests/settings.test.js`: per-profile prefs and the legacy notifications default, language in TMDB requests and the per-language cache, Watchlist release dates, the recap numbers and its Sunday 19:00 time, the auto-backup switch, reset), online accounts in the app (`tests/accounts.test.js`: linking, the server address, signed-out handling, error messages, a new key, signing out and deleting, the key check; against a fake server: `createApp({ server })` takes a function `(method, path, { body, headers })` returning `{ status, body, headers }` or `{ text }`, and records `serverRequests`; no server means every request fails like a lost connection), sync (`tests/sync.test.js`: two devices against an in-memory server; recording, applying, first upload, same-named lists, reset everywhere, prefs, batching, signed out, the v5 upgrade and restore), and the web app (`tests/pwa.test.js`: `sw.js`'s `PRECACHE` matches the files in `public/`, its cache keys, the manifest and icons, every page's head tags, the backup-export record). Not covered: anything DOM-side (`media.js`, page scripts, the picker/profile UI wiring) and the real Capacitor plugins. Check those in a browser by serving `public/` statically (`.claude/launch.json` has an `npx serve` config, with clean URLs turned off in `serve.json` so `page.html?query` isn't redirected to `/page` without its query), and on a phone for anything native.

Values created inside the vm context have that context's `Object.prototype`, so `assert.deepEqual` treats them as a different type. JSON round-trip them first (the tests' `plain()` helper). API responses are already parsed in the outer realm, so they're fine.

## Known gaps

- **The web app on iPhone is only checked by hand.** There's no Mac for Safari's developer tools; iPhone-specific behaviour (status bar colour, safe areas, the share sheet, storage persistence) is verified on a real phone through a preview deploy.
- **No DOM/UI tests.** The test suite covers the data layer, backups and notification scheduling, but card rendering, page scripts and the native plugins themselves are only verified by hand.
- **Backups need the app opened.** The daily background check only schedules notifications. The weekly auto-backup runs on the next app open after it's due, because the background job can't read IndexedDB.
- **Auto-backup can't delete files from a previous install** (Android scoped storage), so after a reinstall the user removes older `Documents/Watchlog` files by hand.
- The old server-backed website's data (from before this repo's rebuild) has no migration path into a local profile's IndexedDB — it's a different storage shape entirely. The server-backed version itself is preserved in this repo's git history (before the local-first rebuild commit) and is also the current state of the separate [Movie-and-Show-tracker-Website](https://github.com/EasyBuster200/Movie-and-Show-tracker-Website) repo.
